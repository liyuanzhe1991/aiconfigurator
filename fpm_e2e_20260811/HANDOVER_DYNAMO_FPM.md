# Handover — dynamo-FPM(自基准运行时)改动全记录:randtok2

交给 dynamo-fpm dev。内容:改了什么、为什么、问题出在哪、怎么改的、结果、
以及还欠什么。所有数字均来自 fpm-all-20260811 战役实测(证据索引见文末)。

## 0. 一句话

dynamo FPM 自基准的合成输入是 `[0]*n`(全零 token),使 MoE 路由退化,采回的
数据带系统性偏差(小 M 偏快 -5~-9%,大 M 偏慢 +15%);改成 **salt 配对的随机
token** 后,prefill 全域(128-8192)与真实流量对齐到 ≤±1.6%。第一版随机化
(randtok)因破坏 prefix 播种曾报废一轮采集,教训在 §3。

## 1. 症状(问题怎么被发现的)

精度战役用"真实流量下的 FPM 流逐步实测"做 ground truth(不是端到端客户端
指标),对账 parquet 时发现:

- decode 稳态:parquet@(64, 531k..582k)=15.43..15.72ms,真实稳态步
  16.94..17.22ms —— **采集数据系统性偏快 8.7-9.3%**,且对 KV 均匀(排除噪声);
- prefill:小 token 档偏快(128 档差 -6ms 量级),8192 档偏慢 +15% ——
  **符号随 M 翻转**,单一常数解释不了;
- 决定性线索:KV 阶梯倒挂(同 batch 下更大 KV 反而更快的采集行),指向
  "被测的计算本身和真实计算不是同一种"。

## 2. 根因

自基准构造合成请求时 token 全为 0:

- MoE 路由器对全零输入产生**退化路由**(所有 token 走同一小撮 expert):
  小 M 时命中的 expert 权重驻留 cache → 偏快;大 M 时 EP 各 rank 负载极度
  不均 → 偏慢(TEP 下木桶效应);
- 判别实验(同引擎、同点位、只换输入):随机 token 后 prefill 128-8192 与
  真实流量差收敛到 ≤±1.5%;换回全零立即复现偏差。归因三重证据
  (temperature 实验 / KV 平坦性 / B 钟形)详见 LEDGER。

## 3. 改动(镜像层,instrumented_scheduler.py 三处替换)

文件:`/usr/local/lib/python3.12/dist-packages/dynamo/vllm/instrumented_scheduler.py`
(dynamo vllm 运行时的 FPM 自基准调度器)。三处 `[0]*N` 替换:

```python
# 1) prefix 播种请求(为 total_kv_read_tokens>0 的点构造已缓存前缀)
- prompt_token_ids=[0] * prefix_tokens,
+ prompt_token_ids=__import__("random").Random(cache_salt).choices(range(1, 199000), k=prefix_tokens),

# 2) 测量请求本体
- prompt_token_ids=[0] * prompt_len,
+ prompt_token_ids=__import__("random").Random(cache_salts[index] if cache_salts is not None else req_id).choices(range(1, 199000), k=prompt_len),

# 3) padding 请求
- prompt = [0] * padded_len
+ prompt = __import__("random").Random(padded_len).choices(range(1, 199000), k=padded_len)
```

### 关键设计:salt 配对(第一版就栽在这)

**randtok v1(废)**:播种方和消费方各自独立随机 → 前缀内容不同 → vLLM 的
block hash(含 cache_salt 与 token 内容)对不上 → 所有 kv>0 点
`fake_prefix_cache_validation_failed`,当轮 **8,914 点阵亡**。教训:我的
判别实验只测过 kv=0 点,盲区放过了它。

**randtok2(现役)**:播种方与消费方用**同一个 salt** 作 RNG 种子,依赖性质
`Random(salt).choices(k=prefix) == Random(salt).choices(k=longer)[:prefix]`
(同种子前缀一致,已单测验证),消费方生成的 prompt 前缀与播种内容逐 token
相同 → block hash 命中。上镜像前在真机验证 8/8 prefix 点通过。

## 5. 结果

- **正式重采(randtok2)**:h200 TEP4/TEP8 × prefill/decode 4/4 cell 通过,
  0 错误,22,217 行,L0 闭环位精确(13,281 点 0.000e+00);
- **prefill 修复达成**:全坐标对齐真实流量(128 档:18.10 vs 真实 18.37;
  8192 档:150.09 vs 150.7);v2 探针离网中位 1.1/2.8%(tp4/tp8);
- **暴露了误差抵消**:旧数据的 TPOT "-6.5% 精度"是 prefill 偏慢与 decode
  偏快互相抵消;数据修对后诚实差距为 -11.9%,全部来自下一条;
- **decode 残余带(本改动不解决,如实记账;tep4 L3 全扫后的完整画像)**:
  graph 态(Bd≤512)、6≤Bd≤300 的自基准数据系统性快于真实 serving,
  钟形:Bd1-4 仅 -1.6~-3.6%,Bd32-256 深至 -11~-17%,Bd≥512 回落 ≈0;
  带内随 kv 一阶平坦(窗内散布 1.8-3.4pp),带深受 per-request kv 调制
  (每请求 kv 越深带越浅:-17%→-7.4%);**极小 kv 窗头是带的最深端**:
  Bd=32 serving 持续 16.5ms vs 采集 9.8ms(-39%),绝对差 ~5-7ms 近似
  恒定、被短步放大。**根因两成分并存(tep4 L3 窗头爬坡直接量化)**:
  (a) 分布差——自基准 decode 步路由的是均匀随机 prompt 尾 token,serving
  decode 步路由的是模型自己生成的 text-like token(EP 热门 expert 偏斜→
  木桶);prompt 随机化(randtok2)修不了这一层,decode 按构造就有。
  证据:扫段窗第 0 步(输入=随机 prompt 尾,与采集同分布)14.0ms,15 步内
  爬到 16.5ms 稳住——爬坡=路由分布过渡,贡献 ~2.5ms(带的 ~40%);
  (b) 环境差——step0 与采集同分布仍差 9.8 vs 14.0ms(~4.2ms,带的 ~60%),
  属 lockstep 自基准 vs serving 每步执行环境(输出处理/调度/同步)。
  **温度判别实验已做(2026-08-12,fpm_e2e_20260811/probes_temp/)**:同引擎
  (decode-parity,默认捕获 512)、同 seed 随机 prompt、C=32、osl=2000,三臂
  只改采样参数:

  | 臂 | 采样 | step0-2(路由随机prompt尾)| 平台[50:400] |
  |---|---|---|---|
  | t0 | 贪心 | 14.24ms | 15.21ms |
  | t1 | 默认(temp1, top_p.95, top_k40)| 14.47ms | **16.32ms** |
  | t2flat | temp2, top_p1, top_k1000 | 14.54ms | 15.01ms |

  读数:①三臂 step0 重合(14.2-14.5,同分布内部对照通过;采样器成本差
  ≤0.3ms,排除 sampler 混淆);②平台随生成分布移动 ——模型自然分布(t1,
  最接近真实流量)最慢,贪心/放平都变快 ~1.1-1.3ms → **分布成分实锤,
  量级 ≈1.9ms(t1 臂内爬坡 14.5→16.3)**;③step0 与采集同分布仍差
  14.3 vs 9.82 → **环境成分 ≈4.5ms,占带的 ~70%,是大头**。
  **async 配置核查(2026-08-12,重要更正)**:decode 引擎(采集 cell 与
  L3 serving 同脚本)**均为 async scheduling 开启**(该 vLLM 版默认 None→
  enabled,引擎日志双侧确认);prefill 引擎双侧均显式 `--no-async-scheduling`。
  InstrumentedScheduler 继承 AsyncScheduler,插桩不破坏 async。
  两个推论:①带的内部效度成立(同配置对同配置),且 decode 真值即生产
  默认语义(async-on);②早先"环境差=sync 调度税/步间隔语义"的机制推测
  **不成立**——serving 的调度 CPU 工作本已被 async 隐藏。4.5ms 环境成分
  是实测事实(同分布 9.8 vs 14.3),但具体环节未定位,候选:async 流水在
  真实负载下的 bubble、采样 token 回填/输出队列路径、benchmark lockstep
  单点无可重叠对象导致测得更"裸"。**GPU 事件审计升为第一优先**;
  剩余判别:②qwen32b dense 对照(无路由,剩余=纯环境差)。
  (已被终审取代 08-20:内容成分经 kvwarm 修复实证 tp4 10.43%→4.80%;
  环境成分坐实为节点异质性 4-6%,噪声注入因果复现;GPU 事件审计与
  dense 对照均裁撤。)
  另记:prefill 为何显式关 async 待考——若生产 prefill 默认 async-on,
  prefill 采集+验证虽两侧一致,但对生产代表性可能有 1-2% 级偏差。
  **RANDKV A/B 判决实验(2026-08-12,probes_temp/benchmark_{zero,rand}.json)**:
  发现 fake decode 的 KV 上下文内容 = torch.zeros 初始化的**全零**

## 6. 战役中发现、尚未修的 dynamo-FPM 侧问题(按优先级)

1. **巨 KV 行坏值:稳态步 wall_time 计算错误(2026-08-12 根因确定;
   "KV 播种/生效失败"假设已排除)**:3 条错误行((256, 6.56M)=11.22ms 真值
   57.46;(481, 2.1M)=12.35 真值 39.77;(496, 1.05M)=17.29 真值 30.97)。
   证据(生产版调度器已从镜像提取:
   `production_instrumented_scheduler_randtok2.py`,3713 行,md5 a338ec5f…):
   ① 三个坏值都低于同 batch 最小 KV 点的耗时(tp8 实测
   (256,512tok)=16.0ms > 11.22;(481,962tok)=25.4 > 12.35;
   (496,992tok)=24.2 > 17.29)→ 该批次的任何一步 GPU 执行都不可能低于
   这个值,所以坏值不是 GPU 耗时,是计时错误;
   ② 批次不可能部分缩水:稳态步对所有请求一起构造,任一请求 allocate
   失败整点作废走超时跳过路径(`_bench_make_steady_step`),该 cell 零跳点、
   零告警 → GPU 实际执行的是全尺寸步;"KV 池耗尽导致抢占缩批"假设同时
   排除(稳态步不走父调度器 schedule(),没有抢占路径);
   ③ 出错的代码:稳态样本的 wall_time = 两次输出**到达时间之差**(L1420
   `model_output_arrival - self._last_update_time`;这样写的动机:async
   scheduling 下 schedule→output 跨度会把 admission 步的等待算进来)。
   到达时间是 CPU 处理到该 update 的时刻,不是 GPU 完成时刻——当 CPU 在
   两次 update 之间被占住,两个输出排队后被背靠背处理,时间差缩小为 CPU
   的处理间隙。停顿来源未定(更正:曾候选 prefix-cache hash 提交,但
   decode cell 实测 `enable_prefix_caching=False`,该候选排除;现候选:
   schedule() 内构造稳态步/allocate_slots ×batch、admission update 的
   逐请求记账,均可用时间线实验测量);
   ④ 坏值随 batch 递增(11.2/12.4/17.3 @ 256/481/496),与 CPU 每请求
   处理成本一致、与 KV 量无关,支持③。
   未闭环:CPU 停顿为何只击中 3/48 个巨 KV 点(竞态,block hash 提交是
   候选原因);admission 步的 FPM 未落盘,无法直接验证被丢失的时间去向。
   **修法(与 §6.5 的计时归因问题同一根因、同一修法)**:基准步计时改
   **CUDA event 在 GPU 上打点**,两处一起根治;落库前加检查——步耗时低于
   max(声明 KV 字节 ÷ HBM 峰值带宽, 同 batch 最小 KV 点实测值)×安全系数
   即标 failed(宁可缺数据,不存错数据)。
   注意:"校验 KV 是否实际生效"的守卫**抓不住这 3 条**(KV 状态本身正确),
   它防的是另一类故障(声明的状态未生效),保留但优先级调低。分层设计
   全文见 `FIX_DESIGN_KV_GUARD.md`(含 2026-08-12 根因更新)。
   **复现实验(2026-08-12 夜,已观测)**:镜像
   `gc-steady-randtok2-tline-20260812`(randtok2 + 仅日志时间线层,勿用于
   正式采集),tep8 decode 同配置重放 batch 256/481/496 全 KV 阶梯 ×10
   (450 点,产物 `fpm_e2e_20260811/tline_bundle/results/`)。结果:
   ① 8/450 样本偏离坐标中位 >30%,全部在 kv≥2M(发生率 9%,正式轮
   3/48≈6% 同量级),双向——塌缩 24.1/26.9ms vs 中位 51.1(坐标即正式
   坏行 (256,6.56M)),倍增 119-127ms vs 中位 62-65(2×,超出 §6.3
   档位抽签幅度);② (256,6.56M) 两个塌缩样本配对该坐标 admission wall
   的前两高(1315.6/1402.2,健康域 1226-1357),唯一偏高样本(67.1)配对

   **落地必须做两处修正(固定 N=11 不可直接上线,2026-08-13 追加)**:
   ① **N 必须自适应,否则毁掉浅 KV 网格**:注入是 `max(1, ctx - N)`,
   per-request 上下文不足 N 时钳位到 1,多个网格点塌缩成同一坐标。实测:
   bs=256 的 kv=512/1024/2048 三点全塌缩到 3,072;bs=481 的
   kv=962/1024/2048/4096 四点全塌缩到 5,772;bs=496 同理塌缩到 5,952。
   而伪影只在深 KV 出现(实测异常率:kv≤131k 为 0%,262k 起 10-40%,
   4M 以上 10-30%),浅点本就不需要多步。规则:
   `N = clamp(1 + ctx_per_req // 100, 1, 11)`,N<3 时退回单步。
   验证:ctx=8→N=1(该处异常率 0%);ctx=545→N=6(窗口占坐标 0.9%,
   5 区间中位,异常率 10%);ctx=25,615→N=11(窗口 0.04%,10 区间中位)。
   窗口宽度恒 ≤ 坐标的 1%,且不再钳位。
   ④ **按步序位的污染率(N=11 数据,70 点 ×11 步)——决定丢几步、取哪几步**:

   | 步序位 | >15% 污染率 | 最大偏差 |

   中第1步异常 11/70,1.18-1.39×,第2步正常,两步和高 8% → 不守恒);
   ②**边界移位**(纯 N=2 实跑观测到 112.50/7.65,两步和守恒)。
   因此**丢前 2 步**(原"丢首步"的建议据此更正),第 4-9 步在 70 样本内
   零污染、最大偏差仅 1-2%。

   网格仍可能有上百行,所以仍建议取中位——**中位不增加任何 GPU 时间**
   (步已经跑了,只是算术),唯一成本是 N。

   第 5 步(数据支持但无冗余)。

   复现性 0.2-1.1%,可容忍;但可直接归零——取 N=10、注入 `ctx-6`、
   测第 2..10 步,窗口中心恰为 `admission_kv + 6×batch` = 目标坐标。

## §6 补充(2026-08-12 多并行战役新发现):第 4 个待修问题

4. **永久不可行 cell 阻塞整个计划的发布**:发布门是"计划内全 cell 通过"
   (runner.py `all_passed and covers_full_plan`),而内存裁决无法证明不可行的
   拓扑(如 M2.7 的 2 卡形状:估算器在 moe 整除性上报错 → 交运行时验证)在
   真机上永久失败后,该计划永远无法发布——8 个通过 cell 的数据被 4 个
   注定失败的 cell 扣为人质,只能收窄形状重跑(全部重采,GPU 时间翻倍)。
   **修法**:运行时验证失败且分类为拓扑不可行的 cell 应落 `infeasible` 终态,
   发布门接受 `passed ∪ infeasible` 覆盖全计划;或允许计划带审计记录地重冻结。
   (归 collector;实测案例:fpm_forward_artifacts/4df9b0f29115c63d)

5. **步计时"借-还"归因伪影(serving 流侧,CPU 步边界差分记账)**:连续
   背靠背的 serving 步中,某步收尾时间戳被延后(晚落的同步点/分配停顿)时,
   该步窗口吞掉下一步的部分执行时间——前步显著变慢("借"),下一步物理
   不可能地快("还",如 Bd=1024 读 2.3M KV 仅记 21.65ms)。tep4 L3 战役
   实锤:19 个慢+快相邻对,全部满足 (慢+下步)/(2×局部中位)≈1.00(守恒),
   一个 1.34 的不守恒反例被正确判为真慢步。影响:真值流的 MAX/P95 被伪影
   霸占(370%/118% 假 MAX);MAPE 无感(~20 对 / 96k 步)。自基准侧因
   点间有不计时间隙、不形成守恒对,但单发采样对"落在被测步内的停顿"无
   防护(与 §6.2 同修法)。**修法**:步计时改 GPU 事件打点,根治两侧;
   验证侧临时对策为打分器配对滤波(score_l3.py 已落地)。
   (证据:fpm_e2e_20260811/l3_harvest_tep4/ 深挖报告 decode §3)
